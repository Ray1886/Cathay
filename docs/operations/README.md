# 貴賓室運營中心 — Codex D 交付說明

基礎版本：`5abcd8f81884fc8f58acf7c18181bfe58368ac37`。交付分支：`feature/operations-dashboard`，按用戶明確要求提交及推送，未合併至 `main`。

## 啟動

Windows 最方便的方式：在專案資料夾雙擊 `start-operations.cmd`，服務會自動啟動並在預設瀏覽器開啟一次性營運入口。保持啟動視窗開啟，按 Ctrl+C 停止。請勿以直接雙擊 `ops.html` 的方式操作資料庫；直接開檔現在會顯示正確啟動方法。

使用 Node.js 24.15.0 以上的 24.x；不需要安裝 npm 依賴。

```powershell
cd C:\Users\XU\Desktop\Cathay-main
npm.cmd start
```

旅客頁：`http://127.0.0.1:8765/`。營運頁：`http://127.0.0.1:8765/ops`。

請使用啟動終端列出的「本機營運一次性入口」登入。入口的隨機憑證位於 URL fragment，不會出現在 HTTP URL 中；前端以同源 POST 換取 HttpOnly、SameSite=Strict Cookie，立即清除 fragment。憑證只能使用一次，Cookie 有效八小時，服務重啟後失效。不要分享入口或終端內容。直接開啟 `/ops` 而未登入，只會顯示授權說明。

所有頁面及 API 同由主服務提供，只監聽 `127.0.0.1`。這是本機示範保護，沒有正式操作員帳號、角色管理或航空公司身份認證。DeepSeek 密鑰仍留在既有主服務內存中；營運測試不需要密鑰。

## 四頁導覽

左欄只有運營概覽、客流預測、人力資源、預約處理。共用日期選擇器和同步狀態，頁首不顯示時鐘。

- 運營概覽：四項摘要、三則今日重點、六堂在場快照及可跳轉的待處理事項。
- 客流預測：依數值生成的 SVG 雙線圖、共用資料的每堂每小時表格、航班與延誤情境控制。圖表範圍可按貴賓室篩選，懸停資料點顯示數值。
- 人力資源：當值／需求差額、每小時需求表與堆疊圖、可展開的示範班次當值表及調度建議。建議不會自動套用。
- 預約處理：真實時段、已確認預約、人工代辦、候補／邀請及近期資料庫事件。日期影響整頁；服務及貴賓室篩選影響時段表、預約表與候補表。頂部卡片明確統計所選日期全部貴賓室。

## 資料來源與定義

唯一預約資料庫仍是 `data/lounge-demo.sqlite`，由 `backend/db.js` 的 `DEFAULT_DATABASE_PATH` 定義，沒有新增第二套營運資料庫。

| 指標 | 來源與定義 |
| --- | --- |
| 已確認預約 | 所選日期 `reservations.status = confirmed` 的服務預約件數 |
| 候補中顧客 | 所選日期有效 `waiting` 記錄按 `user_id` 去重；另列候補記錄筆數 |
| 待確認邀請 | 有效且未過期的 `offered` 記錄數，不計為已確認預約 |
| 可預約時段 | 已啟用、有未保留空位且沒有優先候補的 `direct_bookable` 時段數 |
| 已佔用／保留 | 沿用原服務，未取消預約與未過期邀請計入容量限制；表格另區分 confirmed 與已完成／未到訪的歷史佔用 |
| 目前在場人數 | 選定情境日期 16:00 的合成在場快照；各堂合計，與預約數無關 |
| 客流／人力 | 共用規則模型產生的合成預測，不是航空公司的即時資料 |
| 近期事件 | 共用 `reservation_events`，涵蓋全部日期及貴賓室 |

讀取營運快照使用同一個 SQLite 讀取交易，避免不同進程寫入造成 KPI 與表格各讀到不同版本。預約服務仍管理所有預約寫入、交易、冪等、資格、歸屬、容量及候補優先權。

## 人工預約及時段管理

1. 搜尋並選擇資料庫現有的示範旅客，不能把任意輸入姓名當成身份。
2. 選貴賓室、服務及所選日期的時段。
3. 「新增預約」或「加入候補」先顯示旅客、服務及時間，確認後才呼叫服務。
4. 現有預約下拉選單或預約記錄列可取消指定 `reservation_id`，同樣需要確認。
5. 「查看」時段可檢查預約、候補與邀請；以記錄的真實 `user_id` 和 ID 操作。
6. 接受邀請的操作員代辦只用於旅客已明確同意的示範電話情境；旅客介面仍可自行接受。拒絕邀請／移除候補都呼叫原有取消候補方法。

操作員代辦會檢查會員資格、容量、原有預約重疊及冪等，使用同一寫入交易避免跨進程檢查後競爭。營運端沒有旅客瀏覽器的未保存行程，故不假稱已驗證其登機或完整行程；旅客自行接受邀請仍通過原有完整行程驗證。

新增時段必須選既有可預約服務，時間符合服務時長及示範營業時間，容量為 1–1000（介面預設 1）。拒絕同服務同日期重疊的時段，包括停用記錄；可在詳情重新啟用原記錄。

容量調整不能低於已佔用加邀請保留；增加容量會先按 FIFO 發出邀請。「停用／移除」使用 `active=false` 保留歷史；仍有佔用、邀請或候補時拒絕停用，要求先處理它們。沒有新增直接繞過驗證的 SQL 預約接口。

## 重現完整示範

在預約處理頁選既有種子日期，按「重建示範情境」並確認提示。首次亦可從「載入六堂示範情境」進入。操作只重建 1001、1003、1004、1006，其他時段、歷史預約和事件保留。若日期或示範 ID 與既有資料衝突，整個重建交易回滾。

也可先停止服務，再執行：

```powershell
npm.cmd run demo:ops:reset -- --confirm
npm.cmd start
```

CLI 使用同一資料庫及原種子機制，沿用時段 1001 已有日期；不會自動搬移舊日期。重建建立或沿用旅客 5–8；旅客 1–4 保留原身份設定。

初始情境：1001 為寰宇堂頭等按摩 18:40–18:55、容量 1；旅客 5 已預約，候補依序為 B（2）、A（1）、林小姐（6）。1006 另有王先生的待確認邀請；1003、1004 有其他確認預約。邀請期限沿用五分鐘。

完整演示步驟：

1. 同時開啟已授權營運頁與旅客頁。旅客 A 的候補頁顯示第 2 位。
2. 營運端查看 1001，取消旅客 5 的確認預約。
3. B 依原 FIFO 規則獲邀，A 的等待排名變為 1。名額由邀請保留，沒有自動確認 B。
4. 操作員拒絕 B 的邀請，或等待它過期；A 會獲邀。服務每五秒維護過期與遞補，也可按「處理過期及邀請」。
5. 旅客 A 在旅客頁接受邀請並確認。SQLite 產生已確認預約，候補記錄變為 `accepted`，活動綁定預約 ID。
6. 營運端自動更新確認件數、保留名額及候補排名。資料庫狀態序列為 `waiting → offered → accepted`，並另建 `confirmed` 預約。

重建不是清空資料庫：取消記錄／事件不刪除，ID 不重用，與上述四個時段無關的開發資料不變。如需重建整個資料庫，必須自行備份並明確另行處理，本功能沒有隱式清庫行為。

## 跨介面同步及恢復引擎

營運頁每 2.5 秒查詢受保護快照。旅客頁每 2.5 秒沿用 `ReservationUI.tick()` 讀取可用時段、本人預約和候補，即使面板關閉也更新關聯狀態；頁面重新可見時亦查詢。瀏覽器可節流背景分頁，恢復前景後會更新。

旅客端確認草案存在或提交途中暫停輪詢，避免刷新覆蓋選擇。同步只合併既有活動的預約狀態和 ID，不替換活動時間或插入操作員建立但未與行程關聯的預約；這些記錄仍在「我的預約」可見。接受旅客邀請才按其經驗證的行程草案保存。

`/api/recovery` 的模擬航班結果會通知營運預測模組。營運的合成航班延誤使用現有 `MockFlightProvider`；只更新客流／人力，不把起飛延誤擅自當作旅客登機延誤。延誤覆寫存在服務內存，重啟或重建情境會還原。

## 預測及人力模型

所有頁面使用 `operations-model.js` 的共用數值，圖表從數值生成，不使用參考圖作圖表資產。

已知到訪按同一旅客、同一貴賓室的已確認服務合併：最早服務前 15 分鐘到訪，最後服務後 30 分鐘離開。多項服務不重複增加人數。這是規則推估，不是乘客報到資料。

合成航班每班有目的貴賓室、合資格旅客數與到訪機率。先扣除與該班次相符的已知預約旅客，再將剩餘人數乘機率並四捨五入。離港旅客在預計起飛前 120 分鐘到訪；抵港轉機旅客在預計抵港後 30 分鐘到訪，停留 90 分鐘。延期重算到訪區間。圖表及表格顯示 16:00–20:00 各小時到訪人次，並非同時使用按摩／淋浴的人數。

人力依每小時中點預測在場人數估算；在場需求上限採各堂合成容量，超額另外計算。需求為 `max(最低人手, ceil(預測在場人數 / 示範服務比率) + 已預約按摩的專項需求)`。按高峰時段把有餘裕的一般支援配對至缺額堂，不調走專項人手；無法配對的缺額明示，不杜撰新增員工。

完整示範在高峰可得目前／需要：3/2、4/5、2/2、4/5、3/2、2/2，兩項調動合計仍是 18 人。數值來自模型與同一份合成假設，沒有把參考圖片的 KPI 分散寫進各頁。現場快照為 22 人，與已確認預約 5 件是不同指標。

## API 與共用服務

旅客接口保持原契約：`/api/availability`、`/api/services/slots`、預約建立／取消／換約、候補加入／退出／接受及本人記錄。營運不能冒用旅客 header 取得營運權限。

營運讀取和代辦使用獨立受保護路由，內部重用 `createReservation`、`cancelReservation`、`joinWaitlist`、`cancelWaitlistEntry`、`acceptWaitlistOffer`、`offerAvailableSlot` 等原有服務函式。

| 新路由 | 功能 |
| --- | --- |
| POST `/api/ops/session` | 一次性入口換取限時 Cookie |
| GET `/api/ops/state?date=YYYY-MM-DD` | 日期快照、實際庫存、旅客、預約、候補、目錄及共用預測 |
| POST `/api/ops/actions` | `book / cancel / join / leave / accept / offer`，依操作接受真實 ID |
| POST `/api/ops/slots` | 服務層驗證後新增時段 |
| PATCH `/api/ops/slots/:id` | 容量或啟用狀態 |
| DELETE `/api/ops/slots/:id` | 安全停用，保留歷史 |
| POST `/api/ops/scenario` | 明確確認後重建指定示範時段 |
| POST `/api/ops/flights` | 合成航班延誤重算 |

所有路由驗證 loopback、Host、Origin；寫入要求同源 Origin 及 `X-Ops-Request: 1`。除登入路由外均要求操作員 Cookie。JSON 大小及未知欄位沿用預約 API 驗證。客戶端預約重試沿用同一冪等碼。

## 驗證與限制

基線 121 項測試已先通過。最終共 141 項測試全部通過（新增 20 項），沒有失敗、跳過或取消。新增測試涵蓋指標合計／去重、人力調動、延誤預測、情境重建與衝突回滾、時段新增／停用／容量下限、邀請優先權、一次性授權、跨來源與錯誤身份、完整兩端候補流程、過期、重試、併發、草案保護及直接開檔啟動提示。

執行：`npm.cmd test`。另可用 `node --test tests/operations*.test.js` 只測營運端。UI 單元測試使用輕量 DOM 邊界替身；真正瀏覽器操作另行驗證。

人工 QA：四頁導覽、1600 像素桌面與 420 像素窄螢幕；各頁窄螢幕沒有整頁橫向溢出（表格容器可橫向捲動）；真實 SQLite 取消／拒絕／旅客接受與輪詢同步；時段新增、調容量、人工預約、取消及停用同步；航班延誤重算。瀏覽器沒有捕捉到應用程式警告或錯誤。截圖保存在忽略的 `qa-output/`。

與參考圖的差異：不照抄歷史日期、26 件預約等數字；不製造不存在的餐飲預約或逸連堂服務；在場人數與預約分開；人力表明確區分當值與需求；邀請不算已確認預約；移除採停用保留歷史；使用自製簡單圖形而非官方標誌。

限制：沒有正式登入、真實報到、航空公司庫存或人事系統；預測固定展示 16:00–20:00 合成情境，部分零需求時段是有限航班輸入的結果；不代表全日預測。操作員沒有完整旅客未保存行程，預約代辦只保證資料庫預約規則。歷史事件與取消記錄會累積；重建只針對四個已知示範時段，不清空其他開發資料。營運頁全部新文案為繁體中文，旅客端原有中英文／簡體文案依保持原介面的要求保留。正式部署需另做操作員權限、旅客身份、HTTPS、持久航班事件及稽核。
