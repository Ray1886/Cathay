# 时段预约与候补主界面

运行 `node server.js`，打开 http://127.0.0.1:8765/ ，点击「查看候补」或服务卡片「选择预约」。无需安装依赖，使用 Node.js 24.15.0 以上的 24.x。

## 完成的流程

- 库存直接读取 SQLite，包括日期、服务、地点、容量、占用、邀请保留、可用数量与排队人数。
- 查看当前示范旅客 A 的数据库预约和候补记录；可筛选日期、贵宾室及服务。没有库存或连接失败时不回退固定样本。
- 预约、加入/退出候补、接受/拒绝邀请、取消及换约均有单独确认页。预览与返回不写数据库。
- 创建和换约使用幂等键；网络失败后同一确认页重试沿用同一键。提交时后端重新检查库存、资格、归属及行程。
- 换约采用原后端的事务；新时段不可用时保留原预约。
- 前后端共享 `reservation-model.js` 检查活动时长、重叠、日期、跨日及登机步行约束；服务端还检查与用户其他数据库预约的重叠。
- 活动关联 slotId、reservationId、waitlistEntryId；刷新页面查询后端并同步关联状态。旧本地“已确认”标签不导入数据库，而降为待预约。
- 打开时段页每 5 秒刷新邀请和名次；主服务每 5 秒维护过期与递补。用户接受有效邀请后才生成已预约记录。
- 提交途中行程变化时，数据库结果仍可查询，但不会覆盖新的浏览器行程。

## 文件关系

| 文件 | 职责 |
|---|---|
| server.js | 主页面、DeepSeek、挂载预约 API、数据库与邀请维护 |
| backend/reservation-api.js | 复用原预约路由；主服务通过 beforeMutation 加入旅程校验 |
| backend/reservation-integration.js | 主服务预约意图与已存在预约冲突检查 |
| reservation-model.js | 前后端共享地点映射、时段入行程校验、状态同步 |
| reservation-ui.js | 时段/预约/候补界面，确认、重试、筛选与请求控制 |
| app.js | 活动和预约 ID 关联、入口、存储与风险展示 |
| tests/reservation-integration.test.js | 真数据库与主服务/界面控制器集成测试 |

验证：`node --test` 共 121 项通过，包含新增 9 项整合测试。真实 Edge 浏览器已演示“另一示范旅客占用名额 → A 加入候补 → 释放名额 → A 获邀 → 确认接受 → 刷新恢复预约”，未出现浏览器异常。

## API 兼容性

主服务复用 `/api/services/slots`、`/api/reservations`、`/api/waitlist`、用户记录、取消、换约与接受邀请路由。主界面通过 `X-Demo-User-Id: 1` 使用明确的示范身份，这不是生产登录认证。

在主服务上，预约、候补、换约和接受邀请 POST 请求必须额外提供当前 `context`。缺少行程或冲突分别返回 ITINERARY_REQUIRED / ITINERARY_CONFLICT；与已有数据库预约重叠返回 BOOKING_CONFLICT。独立 4174 API 保持原契约，调用方仍须自行整合行程约束。

主服务 `/api/availability` 现在返回 `{source:'sqlite-demo', slots, dates}`，slot 使用数据库字段，不再是旧 `{type,start,available,queue}` 样本格式。

## 范围与保留限制

数据库地点映射明确为 wing=1、pier=2、deck=5。数据库中的 Wing Business/Pier Business 不等于前端 Wing First/Pier First，未映射路线的地点可查看库存，但不能误当其他贵宾室预约。逸连堂尚无数据库设施，不显示编造时段。

默认库存仅有种子日期。切换到无时段日期显示空列表，不自动重置数据或新增库存。种子数据库中已有预约会显示在“我的预约”，但不会强行插入与当前行程冲突的活动；预约页始终可以管理它们。

浏览器保留行程偏好和关联 ID，预约记录以数据库为准。未关联的数据库预约也会显示；不会将历史预约自动塞进当前行程。行程编辑和恢复草案不自动执行数据库取消或换约，应在预约页明确确认。

规则以示范旅程时间校验，不是机场实时营业预约系统。尚未接生产身份、真实运营库存及国泰航班。DeepSeek 用于对话与行程提案，不可代替用户批准预约事务。

DeepSeek 密钥仍只驻留主服务内存；重启后需通过隐藏输入重新配置，不写入源码或 Git。
